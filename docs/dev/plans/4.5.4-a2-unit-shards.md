# 4.5.4 part A2: the unit suite in four parallel shards – Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** a pull request's unit suite in ~5 minutes of wall time instead of ~9–13, by running it in four shards at once,
with the same files, the same coverage floors and the same ratchet.

**Architecture:** a new matrix job `unit` (shards 1–4) runs `vitest --shard=i/4`, under coverage with a blob report when
the plan's `coverage` gate is on, plainly otherwise. The job named `coverage` (the ruleset requires it by name) needs
`unit`: gate on, it merges the four blob reports with coverage (`vitest --merge-reports --coverage`: the floors of
`vite.config.ts` apply there), runs the ratchet and uploads the summary; gate off, it only says whether every shard
passed. Either way it fails when a shard failed.

**Tech Stack:** Vitest 5 (`--shard`, `--reporter=blob`, `--merge-reports`), GitHub Actions.

**Spec:** `docs/dev/PLAN-4.5.4-SIMPLE-RELEASE.md` part A (G3: a non-product PR in minutes); follows part A
(`docs/dev/plans/4.5.4-a-ci-in-minutes.md`, PR #305), whose ledger ruled that the unit suite runs on every PR.

## Global Constraints
- The same files as today: `test:coverage`'s set (the unit suite and the two asset files, without the nine heavy ones).
- The `coverage` check keeps its name, has no job-level `if` that could skip it, and fails if any shard failed.
- `main` and `full-ci`: coverage on, ratchet `--strict` on `main`, unchanged.
- `pr-gate` needs every job, `unit` included.
- Shell and repo rules as in part A's plan.

## Review Focus
1. One shard red, gate off: `coverage` must be red (not skipped, not green).
2. Gate on: the merged coverage must equal a single run's (floors met the same way; the ratchet reads the same summary path).
3. A shard with no test file (more shards than files in a tiny change): must not fail.
4. `unit` cancelled (a new push): `coverage` is not green.

### Task 1: a package script for the suite without instrumentation
- Modify `package.json`: `test:unit` = `vitest run` with the nine heavy excludes (exactly `test:coverage` without `--coverage`); `test:coverage` stays as is.
- Test (`tests/ci-plan.test.ts` or the package-scripts test that pins scripts, if any): `test:unit` + ` --coverage` equals `test:coverage`'s command.

### Task 2: the `unit` matrix and the `coverage` merge
- Modify `.github/workflows/ci.yml`: job `unit` (needs `plan`, `strategy.fail-fast: false`, `matrix.shard: [1, 2, 3, 4]`, env `RUN` from the `coverage` gate), same setup as today's `coverage`; gate on: `npm run test:coverage -- --shard=${{ matrix.shard }}/4 --reporter=blob --reporter=default` then upload `.vitest-reports/` as `unit-blob-${{ matrix.shard }}`; gate off: `npm run test:unit -- --shard=${{ matrix.shard }}/4`. `--passWithNoTests` on both. Job `coverage`: `needs: [plan, unit]`, `if: always()`, first step fails unless `needs.unit.result == 'success'`; gate on: setup node + `npm ci`, download the four blobs into `.vitest-reports/`, `npx vitest --merge-reports --coverage`, the ratchet, upload `coverage-summary`. `pr-gate.needs` gains `unit`.
- Tests (`tests/ci-plan.test.ts`): replace "runs the unit suite on every change…" with: the `unit` matrix has four shards and reads the `coverage` gate; gate off runs `test:unit -- --shard`; gate on runs `test:coverage -- --shard … --reporter=blob`; `coverage` needs `unit`, has `if: always()`, fails on a non-success `unit`, merges with `--merge-reports --coverage`, runs the ratchet with the same `--strict` expression.
