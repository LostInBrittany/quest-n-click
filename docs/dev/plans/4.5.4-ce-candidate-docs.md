# 4.5.4 parts C and E: the candidate starts itself, the docs publish themselves – Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** after the release pull request merges, nobody starts the candidate by hand; a docs problem shows on the
release pull request (never after the tag) and never holds back npm; a release's docs publish without a click.

**Architecture:** `candidate.yml` also runs on a push to `main` that changes `package.json`'s version (a release
PR's merge); `ship`, `provenance.mjs` and `release.yml` accept that run as they accept a hand-started one. The release
PR's CI runs `npm run release -- check`, which gains the publication check's human gates (`wiki -- check --publish
--reviews-only`, a new flag that leaves out "executed", which needs the candidate's report). The candidate ends with
the full publication check against its own report, as a warning. `docs-publish` runs in release mode under an
environment without reviewers (the signed tag is the approval); the manual modes under `docs-publish-manual`.

**Tech Stack:** GitHub Actions, Node ESM release tools, the wiki's TypeScript check, Vitest.

**Spec:** `docs/dev/PLAN-4.5.4-SIMPLE-RELEASE.md`, parts C and E (S7, S8, S9).

## Global Constraints
- A candidate is still never started by a pull request's push, nor by a push to `main` that does not change the version
  (Dependabot's `package.json` bumps included); `workflow_dispatch` on main stays.
- `ship tag`, `release.yml` and `provenance.mjs` accept exactly two kinds of candidate run: `workflow_dispatch` on
  `main`, and `push` on `main`. Anything else stays refused.
- `npm-stage` and `docs-publish` stay side by side: a docs failure never stops npm.
- The settings (environments, their reviewers and secrets) are the maintainer's to apply: the PR gives the commands.
- Shell and repo rules as in parts A and B.

## Review Focus
1. A Dependabot merge touching `package.json` (dependencies only): no candidate.
2. The release PR's merge: one candidate, on the merge commit, and `ship tag … --candidate=<that run>` accepts it.
3. A release PR with a claim whose review was reset: its CI is red, saying which claim and the command.
4. A manual `docs-publish` (revision, rollback, promote): still waits for a reviewer.
5. The candidate's publication check failing: the candidate is still green (a warning), the release goes on.
